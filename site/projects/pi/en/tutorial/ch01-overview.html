01
L1factarchitecture

01 · 仓库是“通用 Harness 内核 + 完整 Coding Agent 产品层”的双轨架构

SOURCE FACT

packages/agent 的 AgentHarness 直接拥有 session、model、tools、resources、queue 和 hooks；packages/coding-agent 的 AgentSession 仍有自己的 runtime build、resource loader、tool registry、retry 与 compaction 适配。

PLAIN LANGUAGE

一边是可嵌入任何产品的发动机，一边是已经带 CLI、会话、扩展和交互界面的整车；当前两套代码有重叠，不能把发动机的新接口直接当成整车每条路径都已采用。

IMPLICATION

架构抽象领先，但迁移期会产生两个 session/compaction/tool 生命周期，需要明确长期收敛边界。

02
L1factarchitecture

02 · 低层循环把 steering、工具执行和 follow-up 分成内外两层

SOURCE FACT

agentLoop 外层消费 follow-up，内层在 assistant tool call 或 steering 消息存在时继续；每轮发出 agent/turn/message 事件并把工具结果加入上下文。

PLAIN LANGUAGE

用户中途插话会先纠偏当前工作，排队的新任务则等当前回合稳定后再接着做。

IMPLICATION

交互打断与自治续跑共享同一 loop，而不是 UI 另开旁路。

03
L1factarchitecture

03 · 截断响应禁止执行工具；每回合可热刷新完整运行状态

SOURCE FACT

assistant stopReason 为 length 时，即使带 tool call 也不执行，因为参数可能被截断；prepareNextTurn 可替换 context、model、thinking、system prompt 和 tools。

PLAIN LANGUAGE

模型半句话里拼出的命令不会贸然执行；同时下一轮可以换模型、换工具或换说明书。

IMPLICATION

工具安全包含协议完整性检查，动态配置不必重启会话。

04
L1factarchitecture

04 · 新 AgentHarness 把请求 hooks、消息持久化和运行时变更统一到 turn boundary

SOURCE FACT

Harness 在每轮创建 state snapshot，通过 beforeProviderRequest/beforeProviderPayload/afterProviderResponse 包装模型请求；message_end 串行写 session，turn 结束后刷新状态并消费 steer/follow-up；model/tool/resource 变更也持久化并发事件。

PLAIN LANGUAGE

每轮开始先拍一张配置快照，模型请求前后都能挂钩；消息落盘和配置变化在明确边界完成，减少并发写乱序。

IMPLICATION

适合作为自研 Harness 的可复用内核参考，尤其是 transport、storage 和 execution capability 的解耦。
