Plugins and MCP are external devices: docs, device, power, and network must be registered separately.

Answer the chapter question first

How are new capabilities discovered, loaded, called, and removed? Read the implementation as input, state, tool effect, receipt, and recovery—not as a feature list.

L1factconnectors

01 · MCP 工具被统一命名空间化、缓存和动态刷新

SOURCE FACT

ExtensionManager 从所有客户端分页拉取工具，按 extension__tool 前缀公开（特殊配置可不加前缀），缓存聚合结果；扩展增删会提升版本并失效缓存。

PLAIN LANGUAGE

各插件都可能有一个叫 search 的工具，所以 Goose 默认把它们改成“插件名__search”，避免撞名，并缓存工具清单减少重复查询。

IMPLICATION

工具注册表既是性能组件也是一致性组件；热插拔后必须原子失效。

02 · 远端 MCP 支持 HTTP、OAuth 和交互通知

SOURCE FACT

扩展可通过 streamable HTTP（Unix 上还可走 socket）连接，复用凭证存储和 OAuth；工具执行可同时返回通知流、ActionRequired 流与最终结果。

PLAIN LANGUAGE

插件不一定是本机子进程，也可以是要登录的远程服务；执行过程中还能弹出“需要用户操作”的中间事件。

IMPLICATION

Connector 模型必须同时处理认证生命周期、取消、通知和最终值，不能只把工具当普通函数。

L1factconnectors

03 · MCP UI 元数据采用“先剥离、再可信补写”

SOURCE FACT

客户端返回的 goose.mcpApp 和内部工具更新元数据会先被删除；只有宿主主动读取关联资源后才插入可信附件。

PLAIN LANGUAGE

插件不能只靠自己声称“这是可信 UI”就让前端照单全收，Goose 会清掉敏感标记并由宿主重新验证、重新封装。

IMPLICATION

所有能改变宿主 UI/行为的扩展元数据都应有信任边界。
