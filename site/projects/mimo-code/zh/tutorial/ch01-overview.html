    5  ## 摘要
    6
    7  MiMoCode 在共享 Session 引擎上运行 GPT/Codex 模型，同时向它们暴露一套更小的 Codex 风格工具 ABI：`bash`、`apply_patch`、`view_image` 和 `exec`。`exec` 在 QuickJS 中组合经过授权的宿主工具；权限、路径、子进程、取消、持久化和 UI 始终由宿主控制。
    8
    9  ## 核心设计
   10
   11  MiMoCode 没有为 GPT 新建一套 Agent 引擎，而是在统一 Session runtime 上做三件事：
   12
   13  1. 使用 GPT/Codex 专属 system prompt，约定工具选择和调度方式；
   14  2. 通过 `ToolRegistry` 装配更小的模型专属工具 ABI；
   15  3. 提供 QuickJS `exec`，在不扩大权限的前提下组合宿主工具。
   16
   17  ```mermaid
   18  flowchart LR
   19      Model[GPT / Codex] --> Registry[SystemPrompt + ToolRegistry]
   20      Registry --> Direct[bash / apply_patch / view_image]
   21      Registry --> Exec[exec / QuickJS]
   22      Exec --> Tools[Filtered host tools]
   23      Direct --> Host[Permission + path guards]
   24      Tools --> Host
   25      Host --> Effects[Filesystem / Shell / MCP]
   26      Effects --> Session[SessionProcessor / MessageV2 / TUI]
   27  ```
   28
   29  核心原则是：
   30
   31  > 模型决定做什么，`exec` 负责如何组合，宿主决定是否允许以及如何产生副作用。
   32
   33  ## GPT 工具 ABI
   34
   35  [`ToolRegistry.available()`](../../packages/opencode/src/tool/registry.ts#L363) 当前通过模型 ID 判断是否启用 GPT profile：ID 包含 `gpt-`，同时排除 `oss` 和 `gpt-4`。
   36
   37  | GPT 可见工具 | 作用 |
   38  | --- | --- |
   39  | `bash` | 使用 `rg`、`sed` 等检查和搜索文件，并执行命令 |
   40  | `apply_patch` | 以结构化 patch 修改文本文件 |
   41  | `view_image` | 将本地 JPEG、PNG、GIF、WebP 转为模型附件 |
   42  | `exec` | 在 QuickJS 中批量调用和聚合宿主工具 |
   43
   44  GPT profile 会隐藏能力重叠的 `read`、`write`、`edit`、`multiedit`、`grep`、`glob` 和 `notebook_edit`。其他工具仍按 provider、agent allowlist 和运行时 permission 治理。
   45
   46  [`SystemPrompt.provider()`](../../packages/opencode/src/session/system.ts#L24) 独立选择 `gpt.txt`、`codex.txt` 或 `beast.txt`。Prompt 路由与工具 profile 目前是两套字符串规则，尚未统一成模型能力协商层。
   47
   48  ## `exec` 微内核
   49
   50  [`ToolScriptTool`](../../packages/opencode/src/tool/tool-script.ts#L303) 对模型暴露为 `exec`。模型提交一个 TypeScript/JavaScript async function body，通过 `tools.<name>()` 调用宿主工具。
   51
   52  ### 为什么不会绕过权限
   53
   54  [`tool-script-ref.ts`](../../packages/opencode/src/tool/tool-script-ref.ts#L1) 使用 late-bound registry，让 `exec` 取得和外层相同、已经过 model/agent 过滤的 `Tool.Def`：
   55
   56  - 外层不可见的 `read`、`write`、`edit` 不会在 `exec` 内重新出现；
   57  - builtin 子调用执行原来的 `Tool.Def.execute()` 和 `Tool.Context`；
   58  - MCP 子调用仍逐次执行 `ctx.ask()`；
   59  - `exec_command` 只是 `bash` 的别名，权限和执行路径相同。
   60
   61  `task`、`actor`、`question`、`skill`、`workflow`、`cron`、`session` 等控制流工具被排除，因为它们改变对话或调度状态，不适合隐藏在一次脚本调用中。
   62
   63  ### 两层安全边界
   64
   65  1. [`evalScript()`](../../packages/opencode/src/workflow/sandbox.ts#L106) 用 QuickJS 隔离 guest code，不提供 Node、`process`、`fetch`、timer 或模块加载；
   66  2. 真正副作用仍由宿主工具执行，并经过 permission、external-directory、memory guard 和工具自身校验。
   67
   68  QuickJS 只隔离 `exec` 代码。`bash` 仍是真实 Shell，不是容器 sandbox。
   69
   70  ### 资源限制
   71
   72  | 资源 | 默认值 / 上限 |
   73  | --- | --- |
   74  | 嵌套工具调用 | 默认 50，最高 500 |
   75  | 并发调用 | 8 |
   76  | 活跃计算 | 默认 60 秒，最高 600 秒 |
   77  | Wall clock | 30 分钟 |
   78  | Guest 内存 | 默认 64 MiB |
   79  | 代码 / 返回值 / 日志 | 128 KiB / 256 KiB / 64 KiB |
   80  | `files.*` 单文件 | 10 MiB |
   81
   82  `files.readText` 只能读取 worktree 或 OS tmp 内的 UTF-8 文本；`files.writeText` 只能写 OS tmp。项目变更必须调用受权限控制的宿主工具。
   83
   84  ## 其他关键原语
   85
   86  ### `apply_patch`
   87
   88  [`ApplyPatchTool`](../../packages/opencode/src/tool/apply_patch.ts#L24) 在写入前解析所有 hunks、检查路径、计算 diff 并请求 `edit` permission；写入后发布文件事件、运行格式化并刷新 LSP。
   89
   90  它会预验证全部 patch，但多文件写入不是事务性的，中途失败不会自动回滚已写文件。
   91
   92  ### `view_image`
   93
   94  [`ViewImageTool`](../../packages/opencode/src/tool/view-image.ts#L23) 检查模型 image capability、external-directory 和 `read` permission，再验证图片格式并返回 data URL attachment。
   95
   96  当前限制：
   97
   98  - `detail` 只写入 metadata，不改变图片处理；
   99  - 没有独立的图片大小限制；
  100  - `exec` 只传递文本、metadata 和 JSON 值，不能透传图片 attachment，因此图片应直接调用 `view_image`。
  101
  102  ## OpenAI Responses
  103
  104  OpenAI provider 通过 [`sdk.responses(modelID)`](../../packages/opencode/src/provider/provider.ts#L203) 发送请求。[`ProviderTransform.options()`](../../packages/opencode/src/provider/transform.ts#L1275) 默认设置 `store: false`，并为 GPT-5 reasoning 模型请求 `reasoning.encrypted_content`。

    1  # Agent 多 Skill 协同Workflow编排设计
    2
    3  一句话概括：引用多 skill = 用户指定多SKILL和问题，SKILL-Reminder 提示模型创建多SKILL Workflow，最后分解任务落盘解决问题。
    4
    5  ## 一、设计出发点
    6
    7  多 skill 场景下，要解决的不再是"要不要用"，而是"怎么协同"
    8
    9  ❌ 传统触发问题
   10  harness 需要从 query 语义猜测激活哪些 skill，容易漏触发或误触发。
   11
   12  ✅ 显式 /skill 化解
   13  用户在 input 框中直接 /skill-a /skill-b 在 input 框中直写，触发 100% 精确，语义无歧义。
   14
   15  🎯 剩下的挑战
   16  多 skill 之间如何编排：谁先谁后、数据怎么传、冲突怎么裁决。
   17
   18  ## 二、三层职责划分
   19
   20  | 层级 | 职责 | 关键动作 | 失败兜底 |
   21  |------|------|---------|---------|
   22  | 用户层 | 显式 / 声明意图 | /skill-a /skill-b 在 input 框中直写 | 不涉及 |
   23  | Harness 层 | 静态检查 + 注入 Reminder | 解析 frontmatter，检测冲突点，生成 targeted 提示 | 降级为通用模板 Reminder |
   24  | 模型层 | 产出结构化工作流 | 读 SKILL.md → 判定组合关系 → 定契约 → 落盘 | Task-Execution drift 由落盘缓解 |
   25
   26  ## 三、注入位置与时机
   27
   28  核心决策：Reminder 作为 system-injected 消息附加在 user message 之后（对齐 Anthropic 的 long_conversation_reminder 模式），不改写 system prompt。
   29
   30  为什么放 message 层而不改 system prompt
   31
   32  | 维度 | 改 system prompt | 附在 user message 后（选定方案） |
   33  |------|-----------------|-------------------------------|
   34  | 指令遵循率 | 距离 query 远，遵循率较低 | 靠近 query，遵循率明显更高 |
   35  | Prefix cache 命中率 | 污染前缀，每次内容变都破坏缓存 | 前缀保持稳定，动态内容全部下沉到 message 层 |
   36  | 按需注入 | 难以做到 turn 级条件控制 | 只在 @≥2 skill 的 turn 出现，其他 turn 完全不感知 |
   37
   38  条件触发规则
   39
   40  / 单个 skill 时不注入 Reminder。
   41
   42  单 skill 场景没有编排问题，强制规划纯粹增加延迟，还会诱发过度规划（简单任务写三段计划）。触发条件必须精确：
   43
   44  - /count == 0 → 不注入
   45  - /count == 1 → 不注入
   46  - /count >= 2 → 注入 Reminder
   47
   48  ## 四、Reminder 内容设计
   49
   50  关键是让规划产出结构化且可校验的东西，而不是一段泛泛的"我先做 A 再做 B"。
   51
   52  ### Reminder 模板
   53
   54  ```
   55  <skill_composition_reminder>
   56  The user has explicitly referenced multiple skills: {skill_names}.
   57  Before starting work, complete an orchestration plan:
   58  1. Read the SKILL.md of every referenced skill FIRST, then plan
   59     (never plan from skill descriptions alone — the full SKILL.md
   60     may contain constraints that invalidate an imagined workflow)
   61  2. Classify the composition relationship: pipeline (A's output →
   62     B's input) / parallel (each handles a separate part) /
   63     constraint overlay (one does the work, the other provides
   64     rules or standards)
   65  3. If pipeline: define the interface contract for intermediate
   66     artifacts — format and file path
   67  4. If two skills give instructions on the same dimension (output
   68     format / style / process), explicitly declare a conflict
   69     resolution rule: which skill takes precedence on which dimension
   70  5. Output a concise workflow (phase → skill used → artifact),
   71     then execute according to it
   72  Keep planning proportional to task complexity: for simple
   73  combinations, two or three sentences suffice.
   74  </skill_composition_reminder>
   75  ```
   76
   77  ## 五、设计取舍总结
   78
   79  | 取舍点 | 选择 | 放弃的方案 & 原因 |
   80  |--------|------|-------------------|
   81  | 触发方式 | 显式 /skill | 放弃自动语义匹配——不可靠且易过度触发 |
   82  | Reminder 注入位置 | user message 之后 | 放弃改 system prompt——破坏 prefix cache、遵循率低 |
   83  | 触发阈值 | /skill≥2 | 放弃全量注入——单 skill 场景纯增延迟且诱发过度规划 |
   84  | Reminder 内容 | 约束产出结构 | 放弃教具体做法——skill 内容会变，硬编码难以维护 |
   85  | 工作流存储 | 落盘 / Task | 放弃仅存 assistant message——长任务必然稀释丢失 |
   86  | Harness 增强 | 静态预解析冲突 | 放弃让模型自己发现——静态检查更可靠、成本几乎为零 |
