    1  # Agent 多 Skill 协同Workflow编排设计
    2
    3  一句话概括：引用多 skill = 用户指定多SKILL和问题，SKILL-Reminder 提示模型创建多SKILL Workflow，最后分解任务落盘解决问题。
    4
    5  ## 一、设计出发点
    6
    7  多 skill 场景下，要解决的不再是"要不要用"，而是"怎么协同"
    8
    9  ❌ 传统触发问题
   10  harness 需要从 query 语义猜测激活哪些 skill，容易漏触发或误触发。
   11
   12  ✅ 显式 /skill 化解
   13  用户在 input 框中直接 /skill-a /skill-b 在 input 框中直写，触发 100% 精确，语义无歧义。
   14
   15  🎯 剩下的挑战
   16  多 skill 之间如何编排：谁先谁后、数据怎么传、冲突怎么裁决。
   17
   18  ## 二、三层职责划分
   19
   20  | 层级 | 职责 | 关键动作 | 失败兜底 |
   21  |------|------|---------|---------|
   22  | 用户层 | 显式 / 声明意图 | /skill-a /skill-b 在 input 框中直写 | 不涉及 |
   23  | Harness 层 | 静态检查 + 注入 Reminder | 解析 frontmatter，检测冲突点，生成 targeted 提示 | 降级为通用模板 Reminder |
   24  | 模型层 | 产出结构化工作流 | 读 SKILL.md → 判定组合关系 → 定契约 → 落盘 | Task-Execution drift 由落盘缓解 |
   25
   26  ## 三、注入位置与时机
   27
   28  核心决策：Reminder 作为 system-injected 消息附加在 user message 之后（对齐 Anthropic 的 long_conversation_reminder 模式），不改写 system prompt。
   29
   30  为什么放 message 层而不改 system prompt
   31
   32  | 维度 | 改 system prompt | 附在 user message 后（选定方案） |
   33  |------|-----------------|-------------------------------|
   34  | 指令遵循率 | 距离 query 远，遵循率较低 | 靠近 query，遵循率明显更高 |
   35  | Prefix cache 命中率 | 污染前缀，每次内容变都破坏缓存 | 前缀保持稳定，动态内容全部下沉到 message 层 |
   36  | 按需注入 | 难以做到 turn 级条件控制 | 只在 @≥2 skill 的 turn 出现，其他 turn 完全不感知 |
   37
   38  条件触发规则
   39
   40  / 单个 skill 时不注入 Reminder。
   41
   42  单 skill 场景没有编排问题，强制规划纯粹增加延迟，还会诱发过度规划（简单任务写三段计划）。触发条件必须精确：
   43
   44  - /count == 0 → 不注入
   45  - /count == 1 → 不注入
   46  - /count >= 2 → 注入 Reminder
   47
   48  ## 四、Reminder 内容设计
   49
   50  关键是让规划产出结构化且可校验的东西，而不是一段泛泛的"我先做 A 再做 B"。
   51
   52  ### Reminder 模板
   53
   54  ```
   55  <skill_composition_reminder>
   56  The user has explicitly referenced multiple skills: {skill_names}.
   57  Before starting work, complete an orchestration plan:
   58  1. Read the SKILL.md of every referenced skill FIRST, then plan
   59     (never plan from skill descriptions alone — the full SKILL.md
   60     may contain constraints that invalidate an imagined workflow)
   61  2. Classify the composition relationship: pipeline (A's output →
   62     B's input) / parallel (each handles a separate part) /
   63     constraint overlay (one does the work, the other provides
   64     rules or standards)
   65  3. If pipeline: define the interface contract for intermediate
   66     artifacts — format and file path
   67  4. If two skills give instructions on the same dimension (output
   68     format / style / process), explicitly declare a conflict
   69     resolution rule: which skill takes precedence on which dimension
   70  5. Output a concise workflow (phase → skill used → artifact),
   71     then execute according to it
   72  Keep planning proportional to task complexity: for simple
   73  combinations, two or three sentences suffice.
   74  </skill_composition_reminder>
   75  ```
   76
   77  ## 五、设计取舍总结
   78
   79  | 取舍点 | 选择 | 放弃的方案 & 原因 |
   80  |--------|------|-------------------|
   81  | 触发方式 | 显式 /skill | 放弃自动语义匹配——不可靠且易过度触发 |
   82  | Reminder 注入位置 | user message 之后 | 放弃改 system prompt——破坏 prefix cache、遵循率低 |
   83  | 触发阈值 | /skill≥2 | 放弃全量注入——单 skill 场景纯增延迟且诱发过度规划 |
   84  | Reminder 内容 | 约束产出结构 | 放弃教具体做法——skill 内容会变，硬编码难以维护 |
   85  | 工作流存储 | 落盘 / Task | 放弃仅存 assistant message——长任务必然稀释丢失 |
   86  | Harness 增强 | 静态预解析冲突 | 放弃让模型自己发现——静态检查更可靠、成本几乎为零 |
