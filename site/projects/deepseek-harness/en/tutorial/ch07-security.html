Security: approvals, permissions, boundaries

Start with a concrete analogy

Answer the chapter question first

What do approval, capability restriction, and isolation each solve? Think of DeepSeek Harness as a hot-swappable runtime tree: the event log is the black box, the agent loop is the driver, and model/tools/sandbox are replaceable parts.

L2factsecurity

01 · Approval and sandboxing are separate control axes

SOURCE FACT

Tool ask/deny/allow is a policy decision, while sandbox-local confine wraps argv in an OS runner; they live in separate packages and seams.

PLAIN LANGUAGE

Asking the user for permission does not replace limiting which files a command can touch.

IMPLICATION

Security UI and audit logs should show approval and enforcement separately.

02
L1factsecurity

02 · Tool callbacks must honor the caller signal so cancellation is not lost

SOURCE FACT

Around-dispatch may replace exec.signal, but the registry re-fuses the caller signal before the body; listeners must wait for owned work to quiesce.

PLAIN LANGUAGE

Timeout or cancellation must stop the process or network work at a safe boundary, not merely gray out the UI.

IMPLICATION

Cancellation belongs in the tool contract and needs mid-flight tests.
