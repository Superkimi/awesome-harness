Start with a concrete analogy

Context is a workbench that tidies itself: current material stays visible, old material is archived, and indexes remain recoverable.

Answer the chapter question first

What enters context, and what gets compacted or recovered? Think of DeepSeek Harness as a hot-swappable runtime tree: the event log is the black box, the agent loop is the driver, and model/tools/sandbox are replaceable parts.

01 · Stream chunks enter the log before BlockAssembler creates a message

SOURCE FACT

step() calls llm.stream, appends every assistant/chunk, feeds BlockAssembler, then records assistant/message with sourceEventSeqs.

PLAIN LANGUAGE

The UI can show partial text while recovery still knows which chunks formed the message.

IMPLICATION

Streaming UI, audit replay, and model messages should share one causal record.

02 · Provider failures carry structured code, status, and request facts

SOURCE FACT

LlmFailure defines message, code, status, retry delay, and request id; request-error decides retry while other failures remain LlmError.

PLAIN LANGUAGE

A failure is not just a string; the harness can distinguish auth, rate limits, missing adapters, and transport faults.

IMPLICATION

Error taxonomy must feed replay and retry policy instead of being guessed by the UI.

03 · Dynamic context enters the next request through a projection

SOURCE FACT

preStep renders prompt sections through RuntimeContextProjection.project and appends the returned UserMessage to claimed messages.

PLAIN LANGUAGE

Context is not permanently baked into the system prompt; it is generated from session state as a traceable message.

IMPLICATION

Dynamic environment context needs a budget, source, and version rather than hidden injection.

04 · Model-visible input must be reconstructable from the session log

SOURCE FACT

architecture.md states model-visible ⟺ logged: anything reaching a model request must have an event source and be projected by deriveMessages.

PLAIN LANGUAGE

If context exists only in memory, a restart makes the model forget it; it is not a durable input.

IMPLICATION

When adding context, add the event first and then the prompt projection.

   96  **Model-visible means logged.** Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it. This is why a new model-visible input requires a new session event: extend `SessionEventMap` and render from the log.
   97
   98  ## Capability seams
   99
  100  A **seam** is a swappable capability with three roles: a **Service Definition** declaring the interface, a **Service Provider** implementing it, and a **Consumer** using it, commonly a model-facing tool. A package may combine roles, but one role alone is not a seam; adding a capability means designing all three ([capability graph](capability-seams.md)).
  101
  102  Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks. [Subagent providers](subsystems/subagent.md) vary just as widely behind one interface, from a fresh child agent to a delegated turn in another product.
  103
  104  ## Where new behavior goes
  105
  106  New behavior attaches to a documented extension point. Changing the loop itself updates this map.
  107
  108  | Goal | Mechanism |
  109  |---|---|
  110  | Add a model provider | register its adapter on `ctx.llm` |
  111  | Add a model-facing capability | register on `ctx.tools`; its schema joins prompt assembly |
  112  | Give one session a different capability set | compose an agent preset; a service row there needs an `isolate` realm |
