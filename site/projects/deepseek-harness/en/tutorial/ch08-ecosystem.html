01 · LLM, MCP, filesystem, shell, and sub-agents share capability seams

SOURCE FACT

architecture.md defines Service Definition, Provider, and Consumer as the three roles of a seam; a remote sandbox can move Bash, PTY, and LSP together.

PLAIN LANGUAGE

Swapping a provider does not require duplicating logic for every tool.

IMPLICATION

Design the execution world first, then add concrete connectors.

  100  A **seam** is a swappable capability with three roles: a **Service Definition** declaring the interface, a **Service Provider** implementing it, and a **Consumer** using it, commonly a model-facing tool. A package may combine roles, but one role alone is not a seam; adding a capability means designing all three ([capability graph](capability-seams.md)).
  101
  102  Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks. [Subagent providers](subsystems/subagent.md) vary just as widely behind one interface, from a fresh child agent to a delegated turn in another product.
  103
  104  ## Where new behavior goes
  105
  106  New behavior attaches to a documented extension point. Changing the loop itself updates this map.

  108  | Goal | Mechanism |
  109  |---|---|
  110  | Add a model provider | register its adapter on `ctx.llm` |
  111  | Add a model-facing capability | register on `ctx.tools`; its schema joins prompt assembly |
  112  | Give one session a different capability set | compose an agent preset; a service row there needs an `isolate` realm |
  113  | Add shell execution | register a `ctx.shell` backend; the local one spawns through `ctx.subprocess` |
  114  | Add persistent terminal execution | register a `ctx.terminals` backend plus `dsh-tool-terminal` |
  115  | Add a human command | register on `ctx.commands`; it dispatches without a model turn |
  116  | Add background work | register on `ctx.jobs`; `job_*` tools collect or stop it |
  117  | Add filesystem access or policy | register a `ctx.fs` provider or listen to `fs/*` events |
  118  | Confine spawned processes | use a `ctx.sandbox` backend; consumers wrap argv before spawning |
  119  | Intercept a request, tool, or turn | use its `agent/*` or `tools/*` event; `agent/turn-stopping` stops a turn |
  120  | Add model-facing context | call `agent.inject()`; it lands in the next admitted request |
  121  | Add UI or editor integration | drive `ctx.agents` and render from `session/event` |
  122  | Add a Web Client Chat node | register a `ConversationNodeDefinition` + keyed renderer |
  123  | Add durable session state | extend `SessionEventMap`; render and replay from the log |
  124  | Generate session titles | register the sole `ctx.sessionTitle` provider |
  125  | Manage a same-session objective | use `ctx.goals`; continue through `agent/*` |
  126  | Fork a live session | `ctx.sessions.fork(source, boundary?, childSessionId?)` |
  127  | Scope a registration to one agent | use that agent's `agent.ctx` |

02 · The tool pipeline separates decisions from observation with waterfall and emit

SOURCE FACT

tools/pre-execute can allow/deny/ask, tools/execute wraps dispatch, tools/post-execute may transform results, and tools/result observes the frozen final outcome.

PLAIN LANGUAGE

Approval, retry, result transformation, and metrics are pluggable stages rather than hidden branches in one function.

IMPLICATION

Document whether each stage can block, persist, or transform data.
